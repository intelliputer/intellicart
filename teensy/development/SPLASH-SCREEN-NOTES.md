# Intellicart startup-screen notes

Date: 2026-11-11

This note records the implementation and hardware-debugging lessons from
replacing the original RTO-Cart startup ROM with the Intellicart screen.

## Where the screen lives

The TV startup image is **not** an asset on the microSD card.  It is a small
Intellivision-compatible ROM assembled from `splash.asm`, compiled into
`splash.h`, and embedded in the Teensy firmware.  At startup,
`intellicart.ino` copies the 1,280 16-bit ROM words into its temporary ROM
buffer and presents that ROM to the console before opening the SD-card game
browser.

Relevant files:

- `splash.asm` — editable CP-1610/Intellivision source.
- `build_splash.sh` — builds the ROM with the local SDK-1600 assembler and
  generates `splash.h`.
- `../deployment/intellicart/splash.h` — copy consumed by the Arduino sketch.
- `../deployment/intellicart/intellicart-teensy41.hex` — ready-to-upload
  Teensy 4.1 firmware image.

## Build and deployment

From the repository root:

```sh
teensy/development/build_splash.sh
cp teensy/development/splash.h teensy/deployment/intellicart/splash.h
arduino-cli compile --fqbn teensy:avr:teensy41 \
  --build-path /tmp/intellicart-build teensy/deployment/intellicart
cp /tmp/intellicart-build/intellicart.ino.hex \
  teensy/deployment/intellicart/intellicart-teensy41.hex
```

The deployable Arduino IDE folder is `teensy/deployment/intellicart/`.  Open
`intellicart.ino`, select **Teensy 4.1**, and use Upload.  Do not copy the
PNG concept art to the SD card or the Teensy: it is design reference material,
not firmware input.

## Observed console startup sequence

On the real console, the tested sequence is:

1. Power on the console and Intellicart.
2. Press the console **Reset** button.
3. Press **Enter** on Player 1's keypad to leave the lead-in and enter the
   Intellicart game-selection flow.

This is the current expected interaction; it is not a microSD-card action.

## Important EXEC behavior

The Intellivision EXEC always runs the ROM's `TITLE` handler before `MAIN`.
The familiar "Mattel Electronics Presents" lead-in is generated by the EXEC,
not by a bitmap in this project.  `TITLE` can patch its display memory before
returning, while `MAIN` draws the custom Intellicart screen that follows.

Every callable entry routine must begin with `BEGIN`.  It initializes the
CP-1610 return stack.  Omitting it led to an early green screen because a
subsequent `RETURN` used an uninitialized stack.

## Copyright-line patch

The EXEC's lower copyright field begins at display address `$2C9` and has room
for 19 visible characters in this layout.  The final patch is:

```asm
CALL    PRINT.FLS
DECLE   C_WHT, $2C9
STRING  "Copr  2026 cartheur"
BYTE    0
```

The earlier 20-character form, `Copr @ 2026 cartheur`, wrapped the final `r`
onto the next line.  Writing at `$2C0` was also incorrect: it left the
original EXEC copyright field, including `Mattel`, visible.

## Verification performed

- SDK-1600 assembler: zero errors and zero warnings.
- Teensy 4.1 Arduino compile: successful.
- The deployment HEX was copied from the successful compile output and
  byte-compared to it.
- Hardware validation confirmed the standard EXEC lead-in, the removal of
  `Mattel` from the lower copyright field, and the one-line final text.

## Game-surface training notes

The final hardware-validated startup surface is deliberately simple:

- blue color-stack background with a cyan border;
- white `INTELLICART` wordmark;
- yellow `SELECT A GAME` prompt; and
- green `(<)  (o)  (>)` controller cues.

It uses only `CLRSCR` and `PRINT.FLS`, which are known to work in this small
10-bit boot ROM.  This is the safe baseline for future menus, title cards,
and game surfaces.  Keep each composition within the Intellivision's 20 by
12 character grid; prototype it as a proof image before changing firmware.

### GRAM lesson

An experimental version attempted a two-tile-high `INTELLI`/`CART` wordmark
with cyan and purple foreground/background blocks.  It correctly assembled
and compiled for Teensy, but on real hardware the EXEC lead-in appeared and
then video went black when the startup ROM entered the direct GRAM/F/B-mode
path.  Compilation therefore does not validate STIC timing or display mode.

Do **not** write GRAM directly from this short-lived startup routine.  A
future custom-tile surface must use a proper vertical-blank initialization
routine/ISR, following the SDK-1600 GRAM examples, and must be tested first
on hardware with a minimal one-card image.  Keep the color-stack text version
as a recovery build until that staged test succeeds.

### Recommended workflow for future surfaces

1. Design against the 20 by 12 grid and create a proof image.
2. Implement the color-stack/GROM version first with `PRINT.FLS`.
3. Assemble the splash ROM and compile the Teensy firmware.
4. Flash and test the complete console sequence: power on, Reset, Player 1
   Enter.
5. Introduce custom GRAM only in a separate, reversible experiment with a
   vblank ISR; retain the known-good HEX as recovery firmware.
